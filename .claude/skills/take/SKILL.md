# Задача в работу

## Ход работы

1. **Старт.** Прочитай задачу с комментариями (`gh issue view <N> --comments`), заметку «текущая работа» в памяти
   Claude и состояние ветки (`git status -sb`): если ветка `task/<N>-…` уже есть, продолжай в ней. Тело задачи —
   действующее решение, комментарии — история: при расхождении действует тело. Если в «Решении» или «Открытых
   вопросах» есть нерешённое, что влияет на работу, — обсуди с пользователем до начала изменений.
2. **Ветка.** От актуального `dev`: `git switch dev && git pull --ff-only && git switch -c task/<N>-<slug>`, где
   `<slug>` — 1–3 слова латиницей через дефис. Поставь задаче статус: `tools/board.sh status <N> in-progress`.
3. **Изменения.** Делай то, что записано в «Решении» и «Объёме изменений». Изменения вне задачи не вноси — предложи
   отдельную задачу. Тесты пиши по правилам из `TESTING.md`.
   **Для бага сначала падающий тест:** напиши тест, воспроизводящий ошибку, запусти и убедись, что он падает именно из-за
   неё, и только потом исправляй. Для вызова, который должен создавать тест, проверяй сам факт регистрации: зелёная спека
   без единого теста ничего не доказывает.
4. **Решения по ходу.** Если в работе пришлось решить то, чего нет в задаче, или отступить от неё, — согласуй с
   пользователем и запиши в тело задачи (`gh issue edit <N> --body-file …`): в «Решение» (или «Объём изменений»,
   «Критерии готовности») и в «Результаты обсуждения». Затем оставь комментарий — уведомление и история: что и почему
   поменялось (`gh issue comment <N> --body …`).
5. **Памятка и README.** Если задача меняет скиллы, слова или команды процесса, обнови `WORKFLOW.md` в том же PR. Если
   меняется публичный API или подключение библиотеки, обнови `README.md` в том же PR.
6. **Проверка.** Запусти `./gradlew build`: без ошибок и без новых предупреждений компилятора.
   Пройди «Критерии готовности» задачи и отметь выполненные в теле задачи.
7. **Коммиты.** Покажи пользователю итог и получи согласие на коммит. Сообщение — на английском: заголовок, пустая
   строка, пункты.
8. **PR.** `git push -u origin HEAD`, затем `gh pr create --base dev` по шаблону `.github/pull_request_template.md`:
   `Closes #<N>`, изменения, отклонения от задачи, проверки. Поставь задаче статус
   `tools/board.sh status <N> in-review` и дай полную ссылку на PR отдельной строкой. PR — точка сброса: предложи
   пользователю `/clear`.
9. **Замечания к PR** исправляй новыми коммитами в ту же ветку. Сливает пользователь (squash); после слияния
   переключись на `dev` и обнови его.

## Экономия контекста

- **Чтение.** Код не читай целиком: найди объявление или строку (`grep -n`) и прочитай нужный диапазон.
- **Передача.** По слову пользователя «закругляемся» запиши всё незаписанное: решения — в тело задачи и комментарием
  (шаг 4), план — в заметку «текущая работа» в памяти Claude (что сделано, где остановились, следующий шаг). Ответь одной
  строкой, где что лежит.
- **Точки сброса** — после груминга и после PR; посреди работы контекст не сбрасывай: договорённости, не записанные в
  задачу или память, теряются.

## Границы

- В `dev` напрямую не коммить и не пушь: изменения только через PR.
- Не сливай PR и не закрывай задачу сам.
