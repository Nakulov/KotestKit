# Груминг задачи

## Назначение

Превращает тему (баг, API библиотеки, сборка, процесс) в задачу GitHub, готовую к работе: с согласованным решением,
открытыми вопросами и критериями готовности. Файлы репозитория при груминге не меняются.

## Ход работы

1. **Старт.** Прочитай заметку «текущая работа» в памяти Claude и состояние ветки (`git status -sb`); если тема — уже
   заведённая задача, прочитай её с комментариями (`gh issue view <N> --comments`).
2. **Контекст.** Проверь, нет ли уже задачи по теме: `gh issue list --state open --search "<тема>"`. Если есть —
   продолжай её, а не заводи новую. Прочитай связанный код. Посмотри на вехи
   (`gh api repos/{owner}/{repo}/milestones --jq '.[].title'`): если тема меняет порядок этапов, обсуди это с
   пользователем отдельно.
3. **Исследование** — до концепции и вариантов решения. Согласуй с пользователем, какую проблему решаем и для кого:
   - для API — для того, кто пишет тест и кто читает отчёт о его падении, и для движка Kotest, который этот тест
     выполняет;
   - для процесса и документации — для тех, кто читает результат или работает по нему: пользователь, ассистент по
     скиллам, инструменты и доска.

   Задавай вопросы и отвечай на вопросы пользователя. Пока проблема не согласована, варианты решения не предлагай и
   задач не заводи.
4. **Концепция** — до разбора сигнатур и частных решений. Согласуй с пользователем:
   - что это и где его место: вызов DSL, настройка теста, внутренний механизм; что делает библиотека, а что уже умеет
     сам Kotest;
   - на что это похоже в библиотеке и в Kotest. Сначала проверь, ложится ли решение в существующую схему, и только
     потом придумывай новый механизм;
   - общая это проблема или частная. Если вопрос касается многих мест (все арности, все стили спек, вложенные скоупы),
     решай его целиком или вынеси в отдельную задачу, а не особым случаем для одной перегрузки;
   - границы: что входит в задачу, а что — отдельные задачи.

   К сигнатурам переходи только после согласия пользователя с концепцией.
5. **Обсуждение.** Правила для API:
   - начинай с примера вызова в тесте, сигнатура — потом;
   - предлагай альтернативы с рекомендацией;
   - обсуждай по одному решению за раз;
   - различай согласовано, предложено, не определено.

   **API целиком.** Если задача вводит или меняет публичный API, после решений по одному покажи его целиком: все
   сигнатуры, значения по умолчанию, имя создаваемого теста и пример вызова — и получи на него отдельное согласие.
   Ошибки в API (лишняя перегрузка, неочевидный порядок параметров, вызов, который компилируется, но не создаёт тест)
   видны только целиком. Черновик — только после согласия. Для задач без API (процесс, документация, сборка) шаг не
   нужен: итоговые правила целиком видны в черновике.
6. **Размер.** Если тема не помещается в один PR, предложи эпик (метка `epic`) с подзадачами; каждая подзадача —
   отдельный груминг или пункт эпика в Backlog. Если задача меняет и сборку, и API, предложи два PR.
7. **Черновик.** Покажи пользователю задачу по шаблону `.github/ISSUE_TEMPLATE/task.md`: заголовок, метки, все разделы.
   В «Результатах обсуждения» запиши и отклонённые варианты с причиной. Первый критерий готовности — `./gradlew build`
   проходит.
8. **Создание** — только после одобрения черновика, через `tools/board.sh` (раздел «Доска»):
   - задача — `issue`; следующий шаг — только если номер получен;
   - статус Groomed (или Backlog для несгрумленных подзадач) — `status`;
   - подзадача эпика — `sub`;
   - веха этапа — `gh issue edit <N> --milestone "<название>"`, название точно как в списке
     `gh api repos/{owner}/{repo}/milestones --jq '.[].title'`; задача вне этапов остаётся без вехи.
9. **Самопроверка** — всегда, после груминга или заведения задачи. Перечитай задачу (`gh issue view <N>`) так, будто
   видишь её впервые, и допиши недостающее в тело (`gh issue edit <N> --body-file …`):
   - все решения — в теле задачи: комментарии — история, а не единственный источник;
   - для нового API есть сигнатуры и пример вызова, для правила — пример применения;
   - объём: файлы, разбивка на PR, порядок работы, зависимости от других задач;
   - критерии готовности проверяемы;
   - у открытых вопросов понятно, кто и когда их решает;
   - в заметке «текущая работа» — следующий шаг со ссылкой на задачу.

   Если в груминге были промежуточные итоги («Экономия контекста»), пометь каждый строкой в начале
   `**Устарело.** Действует тело задачи.` (`gh api -X PATCH repos/{owner}/{repo}/issues/comments/<id> -f body=…`).
   После груминга всегда оставь итоговый комментарий: `Груминг завершён <дата>. Действует тело задачи.`

   Результат — одной строкой пользователю: «чеклист пройден» или «дописал: …».

   **Холодное чтение.** Если задача создана или погрумлена в этой сессии и в ней есть новый API, правила или разбивка на
   PR, предложи пользователю холодное чтение; запускай только с его согласия. Агент получает только тело задачи, без
   комментариев и разговора, может читать файлы репозитория и отвечает: что сделает первым, какие файлы изменит, что
   непонятно, где задача расходится с репозиторием. Найденное внеси в тело задачи. Если после этих правок изменились
   API или разбивка на PR, предложи второе чтение, тоже с согласия пользователя: новые разделы могут разойтись со
   старыми. Правки формулировок и критериев второго чтения не требуют. Для несгрумленной задачи вопрос другой: хватит ли
   в ней контекста, чтобы её погрумить. Старым задачам Backlog и коротким задачам с очевидным объёмом хватает чеклиста.
10. Сообщи номер и ссылку на задачу. Груминг — точка сброса: предложи пользователю `/clear` перед работой над задачей.

Утверждения о поведении Kotlin и Kotest делай только после проверки, а не по памяти: скомпилируй и запусти пробную спеку
на копии проекта в scratchpad (файлы репозитория при груминге не меняются). Сигнатуры актуальной версии Kotest смотри в
её jar (`javap`) или исходниках. Если поведение пользователю незнакомо, покажи его результатом запуска вместо объяснения
словами.

Темы, которые всплыли по ходу и не входят в задачу, предложи завести отдельно в Backlog с кратким описанием.

## Экономия контекста

- **Чтение.** Код не читай целиком: найди объявление или строку (`grep -n`) и прочитай нужный диапазон.
- **Промежуточные итоги.** В длинном груминге записывай итоги комментариями в задачу блоками «согласовано /
  отклонено / открыто», не дожидаясь конца: при сбросе контекста обсуждение не потеряется. К концу груминга всё
  согласованное переносится в тело задачи (шаг 9).
- **Передача.** По слову пользователя «закругляемся» запиши всё незаписанное: решения — комментарием в задачу (как
  промежуточный итог), план — в заметку «текущая работа» в памяти Claude (что сделано, где остановились, следующий
  шаг). Ответь одной строкой, где что лежит.
- **Точки сброса** — после груминга и после PR; посреди работы контекст не сбрасывай.

## Доска

Доска — проект пользователя `Nakulov` номер 9 «KotestKit». Работай с ней только через `tools/board.sh`; функции в команды
не вставляй:

```sh
tools/board.sh status 7 groomed           # статус: backlog, groomed, in-progress, in-review, done
n=$(tools/board.sh issue "Заголовок задачи" enhancement body.md) &&
  tools/board.sh status "$n" groomed && tools/board.sh sub 3 "$n"
```

- `status` добавляет задачу на доску, ставит статус и проверяет, что она видна в списке доски (почему так — в
  комментарии скрипта).
- `issue` создаёт задачу и печатает номер; падает, если номера нет, — следующий шаг цепочки не выполнится.
- `sub` привязывает задачу к эпику.

Если `status` вернул ошибку, сообщи пользователю: задача создана, но на доске не видна. Вторую метку добавь после
создания: `gh issue edit <номер> --add-label <метка>`. Поле Priority (P0, P1, P2) скрипт не ставит: предложи значение в
черновике и выстави его на доске через `gh project item-edit`.

Метки: `bug`, `enhancement`, `documentation`, `build`, `process`, `epic`.

## Границы

- Не создавай задачу без одобрения черновика и не меняй файлы репозитория.
- Не выдавай предложенное за согласованное: нерешённое остаётся в «Открытых вопросах».
