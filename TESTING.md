# Как мы пишем тесты

## Правила

- Тесты пишутся только как спеки Kotest.
- Внешние спеки на `StringSpec`. `BehaviorSpec` только там, где сама проверка касается Given/When/Then.
- Спека соответствует файлу, где объявлен публичный вызов, пакет тот же: `ShouldReturnTestExt.kt` →
  `ShouldReturnTestExtSpec.kt`, `GivenExt.kt` → `GivenExtSpec.kt`. Спека заводится, когда на файл появляются
  первые тесты. Вызов вместе с `options` проверяется там же.
- Файлы без вызовов для пользователя (настройки, например `TestOptions.kt`) своих спек не получают, они проверяются
  через публичные вызовы.
- Тестовые данные, только если нужны, лежат в `<Имя>SpecData.kt`. Именованных классов-спек там нет: такой класс Kotest
  запустит как настоящий тест.
- Что произошло при прогоне, проверяем через помощники `run<Стиль>Spec`, например `runStringSpec` и `runBehaviorSpec`.
  Спеку для прогона описываем в их лямбде, а не отдельным классом.
- Для бага сначала падающий тест. Зелёная спека без единого теста ничего не доказывает.
- Исключение: пакет `readme` хранит примеры из `README.md`. Они написаны на `BehaviorSpec` и по стандарту из README,
  файлам с вызовами не соответствуют, классы-спеки лежат рядом с тестируемыми классами. Сверку с README выполняет
  `ReadmeSyncSpec`.

## Проверка прогона спеки

Помощники из `src/testFixtures/kotlin/io/github/nakulov/kotestkit/testing/RunSpec.kt` прогоняют спеку из лямбды и возвращают
отчёт: `tests` и `specError`. Есть для каждого стиля: `runStringSpec`, `runBehaviorSpec`, `runFunSpec`, `runDescribeSpec`,
`runFreeSpec`, `runWordSpec`, `runShouldSpec`, `runExpectSpec`, `runFeatureSpec`. Сами они ничего не проверяют, проверки
пишутся матчерами Kotest. Если сломался движок Kotest, помощник бросает его ошибку: такому отчёту нельзя верить.
Помощники — test fixtures корня: тесты корня видят их сами, модуль подключает `testImplementation(testFixtures(project(":")))`.
Fixtures не публикуются.

У теста в отчёте есть `path`, `name`, `prefix` (префикс стиля, например `Given: `, иначе `null`), `type` (контейнер или
конечный тест), `config` и `result`. `childrenOf(path)` отбирает прямых потомков контейнера, а `inEachContainer` выполняет
блок в каждом контейнере `BehaviorSpec`; их пути лежат в `BEHAVIOR_CONTAINERS`.

```kotlin
"вызов создаёт один успешный тест" {
    val run = runStringSpec { "t" { } }

    run.tests.single().result.isSuccess shouldBe true
}
```

Как ведёт себя прогон (проверено на Kotest 6.2.6):

- Ноль тестов для Kotest не ошибка: спека `Success`, ошибок движка нет. Ловится через `.single()` или `shouldHaveSize`.
- Исключение в теле спеки: 0 тестов и заполненный `specError`.
- Отключённый тест: приходит как `Ignored`, `config.enabled == false`.
- Родитель остаётся `Success`, когда упал вложенный тест: результат смотрим у самого `Then`.
- Падение внутреннего теста не роняет внешний, внутренние тесты не попадают в его отчёт.

## Покрытие

Покрытие строк считает Kover, порог 100% проверяет `koverVerify`. Задача входит в `check`, поэтому непокрытая строка роняет `./gradlew build` и локально, и в CI:

```
Rule violated: lines covered percentage is 99.516900, but expected minimum is 100
```

Какие строки не покрыты, показывает `./gradlew koverHtmlReport`.

Порог не ловит (проверено на Kover 0.9.11):

- заглушку `@Deprecated(level = ERROR)` без теста: Kover такие заглушки не считает;
- функцию, которая вызвана в тесте, но без проверок;
- непроверенную сторону условия в одну строку: `if (x) 1 else 2`. Ветки порогом не закрыты.

Эти случаи остаются за чтением кода.

Строки, которые нечем покрыть: порог не снижаем. Исключение из подсчёта делаем только явно, с причиной в описании PR.
